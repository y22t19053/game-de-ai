# 历史智慧入口（怎么被调用）

给创作者用的一句话：**你带着一个问题来，我带着一个历史结构回去；如果库里没有合适的，我直接说没有。**

## 什么时候调我

出现下面任一情形时读本文件（也见 `SKILL.md` 模块表「历史机制」行）：

- 「我想做一个有新鲜感的玩法，但不想套常见模板」
- 「我想要历史质感，但不想做成古风皮肤」
- 「信息呈现/资源管理/风险选择能不能更有特点」
- 「历史上有过什么巧妙的解法能借」
- 「想让一个普通交互有更独特的机制和后果」

不必是历史题材。**借结构不借外观**，所以科幻、现代、卡通风都能用。

## 成档前必过的八道判据（2026-11 起，实测有效）

这些判据是在真实生产流水线（`experiments/aaps/pipelines/history-case.mjs`）里跑出来的，用来防止"看起来齐、其实是编的"。新增案例前逐条过一遍：

0. **首行必须是 `# 档案标题`，紧跟一行 `> 分类 … · 地域 … · 时代 … · 证据等级 …`**。01–18 多为老体例；19–32 这批流水线产物原本直接从 `## 1 历史事实` 开始、没有标题，2026-11-17 已补齐，并把它做成发布闸门（`evaluateDoc` 的 `hasTitle`）——查的是"第一条非空行是不是 H1"，不是数量。
1. **来源行必须可核算**：产物里有一行 `来源：URL 共 N 条，正文可用 M 条`，且 N/M 与实际抓取一致。只说"参考了多篇资料"不算。
2. **单条来源不足 200 字符不可作引用**：抓到的是验证页/拦截页时，正文虽能取到但等于没有。引用它算硬缺口。
3. **分歧必须并列，但只有硬分歧才要求并列**：多字朝代（隋唐/北宋）、年份、数量级差 → 必须并列两说；**单字朝代（唐/明/清）多来自人名书名或合成词，属可能误检**，只许在末行"存疑"里点一句，不许写成年代分歧（这条错了会把假分歧写进档案）。
4. **书名类专名要回源核对**：《…》里的书名在抓取正文里找不到同名写法时，写进 notes 提示人看；**不作为不通过的理由**（人名/地名无统一分隔符，误报率高，不做机械核对）。
5. **降级要摊到验收人面前**：某来源抓取失败时，正文若写"三份来源均可访问"即判不通过；少写一条来源本身不算错。
6. **生产说明必须写「任务 id + 费用」**：`任务 …` 与 `费用：$X（任务总花费，含 plan/run/verify）` 两样都要有，金额要与 `tasks/<id>/task.json` 的 `spentUsd` 对得上（容差 5%，两次运行的档案写两次之和）。起因：3 份档案只记了 run 阶段的花费、2 份根本没记，2026-11-17 已订正；`doctor` 的 `archive-provenance` 项会持续核对。
7. **成档走一条命令，不要手抄**：`node pipelines/publish-case.mjs --task <id> --slug <编号_slug> --note <说明.md> --find "<候选行前缀>" --reviewed-ok`（在 AAPS 仓库 `experiments/aaps/` 下执行；脚本路径 `experiments/aaps/pipelines/publish-case.mjs`）。它会做结构自检、拒绝重复发布、并只改候选表的「初核」列与库存合计（`STATUS_COLUMN = 5`，第 42 轮曾把状态写进「年代」列）。

四条诚实边界写在这里，免得下次又忘：**数字断言只能建议**（同量级不同口径会把每窖产量和全仓总量比成"矛盾"）；**判据一进硬闸门，假阳性就会被模型忠实写进产物**；**"判定不通过"不等于"结构对"**（第 37 轮：来源行写对了内容却放进了第 1 节）；**征引人物/专名时以通行写法为准，来源转写丢字要人工订正**（京相璠 / 《四库全书总目》）。

## 七步调用（不要跳步）

1. **先问清真正的问题**：玩家现在**看不懂**什么、**赌不起**什么、**不信**什么？——说不清就先问，不要翻案例。
2. **从索引里挑 1–2 个**相关案例（见下表），**不要一次展示一大堆历史知识**。
3. **讲清证据边界**：这个说法是"已证实/较可信/有争议/暂无法确认"（口径见 `V21_VERIFICATION.md`）。
4. **只提炼一处可转译的结构**，并做"换词检验"：把历史名词全换成现代词后还成立吗？不成立就不是结构。
5. **给 2–3 个互不相同的转译方向**（不同机制，不是不同配色）。
6. **每个方向写清成本、风险、缺点**，并指出最容易出现的误用。
7. **由创作者决定是否采用**；采用后只留一句"借的是哪条结构"进项目档案。

## 没材料时怎么说

"库里没有直接对应的案例。"——然后给两条可选项：①用现有的六类方法从零推导（不挂历史）；②把它记进"待研究"清单，不强行牵扯。**不许为了显得博学而硬套一个不相关的案例。**

## 两条硬约束

- **不为了体现历史价值而强行用双联/剖面/刻度**：这三样是三种作答语言，一屏只该有一种（见 `V21_METHODS.md` 用法第 2 条）。
- **不把历史案例升级成规则**：它不进 G1–G7，不进考成台账，不做审批依据。

## 成本感

- 一次调用通常只需读 1 份方法卡（约 30 行）＋（必要时）1 份案例档案；**不需要读全部 32 份**。
- 出方案的时间主要在"换词检验"和"三方向差异化"，不在查资料。
- 档案是按"问题"分组的（上表第三列就是那句可借的结构），所以先看表、再决定读哪一份，别从 01 开始顺读。

## 低证据案例（「证据不足」体例）的成档规范

不是每个案例都能写成「办法有效」。有些题材（如 51 希腊火）原始文献缺失、装置无实物，硬写机制就是编。这类案例要按下面的方式成档，否则不许转正：

1. 首行 H1 与体例行照旧，但体例行的证据等级必须写「低」，并注明缺的是什么（配方？结构？原始文献？）。
2. 正文 8 节结构照旧，但第 3、4 节只写**材料确实记载了的机制**；材料没说的，写「材料未载」，不写推测。
3. 第 8 节必须有三层：材料所载的可信史实 / 同时代描述的效果 / 后世推测（标明是推测）。
4. 必须有独立的「存疑：」行，列出本案回答不了的问题（谁发明的、什么时候第一次用、怎么造、什么时候停用），且不得用「一般认为」把存疑抹平。
5. 来源行的数字必须等于本任务真实的抓取次数与正文可用条数（失败的那次可以写进「主要来源」段并注明 404/未引用）。
6. 转译节（第 7 节）只转译机制与限制，不转译虚构配方；可以写「玩家的取舍」，不能写「武器的参数」。

这套规范的用处：它让「证据不足」本身成为可交付的结论，而不是失败；也让下游引用时知道该案例能支撑什么、不能支撑什么。
