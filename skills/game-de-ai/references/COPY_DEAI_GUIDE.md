# COPY_DEAI_GUIDE — 游戏文案去 AI 味工作流

**用途**：写或改玩家能看见的每一句中文。
**和 `voice-deai` 的分工**：voice-deai 处理**署名长文**（小说、公众号、社媒稿），靠作者本人的语料学语气；本指南处理**游戏内短文案**——句子短、类型多、嵌在数值和交互里，且有工程约束（变量、占位符、HTML、ID）。两者可以同项目并用，但不要互相替代。
**铁律**：先分类，再写；先场景，再句子；不改程序读的东西。

---

## 1. 开工六问（缺三条就别动笔）

| # | 问题 | 拿不到的后果 |
|---|---|---|
| 1 | 这段文字属于哪一类？（查 `GAME_COPY_TYPES.md` 十类） | 用旁白腔写按钮 |
| 2 | 玩家此刻在做什么？（选、读、听、查） | 字数与语气错位 |
| 3 | 它出现在哪？（屏幕位置、是否需要一行内读完） | 写长了必被截断 |
| 4 | 此刻发生了什么？（时间、地点、前一秒的事件） | 只剩空泛形容 |
| 5 | 谁在说？（人物、年龄、职业、和玩家的关系） | 全员同声 |
| 6 | 要玩家得到什么？（知道一个数、做一个决定、感到一件事） | 写了但没有用 |

答不全时：先写一版「信息正确但平淡」的，标 `[待场景]`，不要用形容词去填空。

## 2. 生成时就别长出 AI 味（顺序不能反）

1. **先定类型和长度预算**（见 COPY_TYPES 表），写在草稿第一行注释里。
2. **再取该项目 Voice Bible**（`<游戏工程>/visual/COPY_VOICE_BIBLE.md`）；没有就先建一份，见 `templates/COPY_VOICE_BIBLE.md`。
3. **先写一个具体事实**：几点、几号、多少钱、谁做了什么动作。这一句是骨。
4. **再加人物/场景的一个细节**：一个声音、一个物件、一个身体动作。
5. **最后才考虑语气词、省略、比喻**；加之前问「这个人此刻会不会这样说」。
6. **删掉解释句**：凡是在向玩家解释他已知的信息，删。

反过来的顺序（先写漂亮句子再补事实）必然产出模板文案。

## 3. 三档处理：先判档，再动手

| 症状 | 档 | 动作 | 输出 |
|---|---|---|---|
| 只有一个词不自然、错字、语气过正式 | 局部修正 | 只改该词/该句，其余原样 | 改后文本 + 一行原因 |
| 一句话结构不对（被动、过长、翻译腔） | 句子重写 | 保信息、换句式 | 原句 → 新句 |
| 整段信息组织不对（顺序、主次、重复） | 段落重组 | 可调顺序、可删，不可加事实 | 前后对照 + 调了什么 |
| 通篇是同一套腔调/句式 | 全文重写 | 按 Voice Bible 重写，保留全部事实与工程记号 | 新稿 + 变更说明 |
| 文字没问题，是结构问题（该拆屏、该改流程） | 提结构调整建议 | 只提建议，不在文案层硬解 | 建议 + 影响面 |

**优先选对原文影响最小的有效改动**。能改一个词就不要重写一句；能重写一句就不要重排一段。

**篇幅守恒**：改写前后长度应落在 **4/5 – 5/4** 之间（同一条文案）。
明显变长＝在解释、在补形容词；明显变短＝在丢信息。两种都要回看。

**结构层要先授权**：凡是改到「信息怎么组织」的（拆屏、重排、合并两条提示、把解释挪走），
属于结构层改动——先说清动哪一处、影响哪个界面，得到确认再动。
只改词句的属表面层，可直接做。

## 4. 三层复核（每一次改写都过一遍）

**第零步·先分表面/结构**：这一段的问题是「词不对」还是「组织不对」？
只清表面痕迹的质量提升极小（上游实测 +1.6 点），先看结构：有没有同一情绪反复写、信息够了还解释、把复杂结果压成单一原因。

**第一层·语言层**：套 `CHINESE_AI_PATTERN_CATALOG.md` 的 P01–P46 扫一遍。
只报**有证据**的：指出具体的词/结构（「这屏 5 个按钮里 3 个是四字成语」），不写「略显模板」。
单条弱信号不判，三条以上的合成信号才算（见 CATALOG §5.1）。
需要机械口径时跑 `scripts/copy_scan.py`（密度阈值 5/千字），它只负责找「该回头看的段落」，不判对错。

**第二层·场景层**：四问——
1. 这句话在这个时刻、这个地点成立吗？（凌晨四点不会说「今天辛苦了」）
2. 这个人会这样说话吗？（老板 vs 学生 vs 城管）
3. 它和屏幕上的其他字冲突吗？（同一屏两个语气）
4. 它需要玩家已经知道什么？玩家知道吗？

**第三层·整体层**：把同类文字**排在一起读**——
- 十个按钮连读，是不是同一个句式？
- 五条系统提示连读，是不是同一种客服腔？
- 两章旁白连读，是不是同一个比喻系统？
- 跨项目对照：和另一款游戏的文案有没有变成同一套？（V0.2 的硬验收项）

## 5. 事实与工程保护（硬边界）

| 必须原样保留 | 可以改 |
|---|---|
| 人物名、地名、专有名词 | 描述这些名字的句子 |
| 数值、单位、日期、时间 | 数值前后的自然语言包装（不改数值写法） |
| 规则描述里的准确条件（「3 回合内」） | 语序、语气 |
| 道具/卡牌/菜品名称（若已定名） | 名称前后的修饰句 |
| 变量与占位符：`{name}` `%s` `{{}}` `$var` `{0}` | 它们周围的文字 |
| 事件 ID、分支键、代码标记、HTML 标签、注释 | 标签之间的可见文字 |
| 程序读取的固定字符串（存档键、成就 ID、埋点名） | —— |

三条操作规则：
1. **改前先分类**：把待改文本拆成「可见文案」与「工程记号」两列；只动第一列。
2. **占位符用占位保护**：改写时保持占位符原样、个数不变、位置尽量不变（顺序变化会破坏多语言/参数映射）。
3. **不补事实**：不新增人物经历、背景、因果、承诺、数值。「她父亲是医生」这种句子，原文没有就别写。

发现原文事实错误时：**标注，不改**，交用户决定。

## 6. 六种工作模式

| 模式 | 输入 | 输出 | 不做什么 |
|---|---|---|---|
| 文案诊断 | 现有文本 | 问题清单（位置 + 证据 + 建议） | 不改文本 |
| 轻度润色 | 现有文本 | 改后全文 + 逐条 diff | 不动结构 |
| 深度改写 | 现有文本 + 场景信息 | 原/新对照 + 变更理由 | 不加事实 |
| 文风匹配 | 新文本 + Voice Bible | 符合该项目的文本 | 不统一成「通用好文笔」 |
| 批量审校 | 一批文案 + 类型标注 | 分类表 + 分级清单 + 建议动作 | 不一次性重写全部 |
| 文案创作 | 场景 + 人物 + 类型 + 预算 | 新文本（可给 1–3 版） | 不写占位符、不编设定 |

**作为视觉工作流的内部步骤时**（工部实施、礼部材料），只返回最终文案，不附自评长文。

## 7. 批量审校流程（一次改一个项目）

1. **提取**：只取玩家可见字符串（HTML 文本节点、`const` 文案对象、i18n json、组件内 `"中文"`）。排除注释、ID、日志。
2. **分类**：按 COPY_TYPES 打 1–10 类型标签；无法归类的单独一列（通常是漏掉的界面）。
3. **机械扫**：跑 `scripts/copy_scan.py`（确定性规则，零幻觉）拿到候选清单。
4. **人工分级**：必改（错/误导/明显 AI 腔）／建议改（可读但平庸）／不动（本来就好，别碰）。
5. **逐条改**：一条一个记录（原文、改后、原因、类型）。
6. **回灌**：改后的文案按类型回填工程；同时更新 Voice Bible 的「已认可例句」。
7. **复核**：同类文字连读；截图看真实排版（长文案是否换行、按钮是否溢出）。
8. **出覆盖率回执**：`共判 N 处 · hard 命中 a · strong 命中 b · guideline 命中 c · 不适用 d`。
   回执是这次批量的完工证明；没有回执＝没审完（超过 20 条时人会抽查三条就收工）。
9. **留档**：原文与改后各存一份（`visual/v02_test/` 或项目 `copy_baseline/`），保证能一键还原。

## 8. 与其他部门/模块的接口

- **工部**：文案必须能在真实界面里放下（按钮 ≤ 4 字、提示 ≤ 2 行）；改文案后必须重截图。
- **刑部**：字数、术语、标点、数字写法属规范；同一术语全项目统一（见 VISUAL_LANGUAGE 的用词表，如有）。
- **户部**：素材名/文件名不进 UI；UI 文字由前端渲染，不烘进图片。
- **门下省**：文案任务可由门下省独立审议——它拿原稿 + Voice Bible + 类型标注，先独立改写 3 条，再对我的稿子提异议。

## 9. 自检（交付前）

- [ ] 每句都能说出「谁、在哪、什么时候」？
- [ ] 同屏同类文字句式是否 ≥3 句雷同？（是就改一处）
- [ ] 有没有解释玩家已知的信息？
- [ ] 形容词删掉后信息是否还在？
- [ ] 占位符、数值、名称、标签是否零改动？（用 diff 核对）
- [ ] 有没有新增任何原文没有的事实？
- [ ] 两款游戏的文案放一起，能分出是谁吗？
- [ ] 真实截图里有没有被截断/换行难看？
- [ ] 是否给了覆盖率回执（判了几处、各档命中几处）？
- [ ] 改写前后长度是否保持在 4/5 – 5/4？结构层改动是否已授权？

## 10. 反例（这些做法等于没做）

1. 建一张禁词表，把所有「然而/此外」删掉就算完成。
2. 把所有句子改成短句 + 脏话，声称「有人味」。
3. 把 AI 检测器分数当验收标准。
4. 一次重写全项目文案，不做对照、不留原文。
5. 改写时顺手「优化」了数值、名称、ID。
6. 两个项目共用一套 Voice Bible。
