# 跨项目反馈登记规范

> 目的：让真实项目的问题能到 DE-AI 手里，同时**不让单个项目的偏好变成所有游戏的法律**。

## 三类反馈，去向不同

| 类 | 是什么 | 例子 | 去向 |
| --- | --- | --- | --- |
| **A 项目专属** | 只对这个项目成立的设计/文案/空间判断 | 「《午夜狂欢》的厨房六区得按出餐节奏排」 | 留在项目档案，**不进 DE-AI 通用规范** |
| **B 可复用** | 在多项目反复出现的缺陷或误判 | 「深色玻璃面板在饱和霓虹场景里总是读成占位框」 | 提交 DE-AI 研究，须带**原始项目 + 版本 + 证据 + 适用范围** |
| **C 系统缺陷** | DE-AI 自己的工具/制度坏了或太贵 | 「编译器把生成物也扫了，报 18 处假阳性」 | 进 DE-AI 修复队列（优先） |

## 一条反馈的字段（缺一项就不收）

```
项目：           bistro-rush
版本/提交：      v12 / 85a8451
类别：          B（可复用）/ C（系统缺陷）/ A（项目专属，仅登记）
现象：          一句话说清发生了什么（不要写"体验不好"）
证据：          截图路径 / 文件:行 / 命令输出 / 实测数字
适用范围：      哪些场景会重复出现，哪些不会
已试过的解法：  失败的那个也写（避免 DE-AI 再推一遍）
建议动作：      修工具 / 改规范 / 只登记
登记日期：      2026-11-15
```

## 收与不收

**收**：有证据、能说清适用范围、能指到文件或运行结果。
**不收**：只写"感觉更好看"、把一次成功当普适规律、要求改别的项目的工程或文档、要求为它开一次庭。

## 从 B 到通用规范的门槛

一条 B 类经验要写进 DE-AI 的通用规范（`ANTI_AI_PATTERNS` / `DESIGN_LESSONS` / `COPY_DEAI_GUIDE` 等），至少满足一条：

1. **两个以上互不相同的项目**各自复现过，且方向一致；
2. 一个项目内有**可复现的实测**（数字/截图/复跑），且写清"只在该条件下成立"。

不满足就标 `[假设]`，不许以规范口吻写。

## 登记放在哪

- DE-AI 侧：`references/governance/FEEDBACK_LOG.md` 追加一行（项目 / 版本 / 类别 / 一句话 / 处置）。
- 项目侧：留在该项目自己的复盘文件里（如 `visual/V12_NOTES.md` 的"没做/留账"节）。

> 单项目的成功 ≠ 通用规则；单项目的失败 ≠ 全体禁用。证据在哪儿，结论就到哪儿为止。
