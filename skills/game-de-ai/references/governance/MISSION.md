# GAME DE-AI 最高层目标（协议 V0.1 · 2026-11-15）

> 本文件优先级高于本技能内的一切方法、制度与工具文档。任何机制若与本文件冲突，以本文件为准。
> 用户下达的补充目标协议原文要点在此；冲突时以用户最新指令为准。

## 唯一核心目标

**研究、识别、减少和预防 AI 参与游戏创作时产生的模板化、机械化、同质化与缺乏作者判断的问题；
帮助 AI 参与制作的游戏形成真正独立的设计逻辑、视觉身份、内容密度、交互性格和可信细节。**

一句话：**我们只是想让 AI 做出来的游戏，少一点 AI 味。**

最终检验对象是**作品**，不是 DE-AI 自己。
文法、仪器、法庭、三省六部、G1–G7 全部是手段；手段复杂不等于目的达成。

## 六类 AI 味（研究方向，不是统一审美清单）

| 类 | 表现 |
| --- | --- |
| 视觉 | 千篇一律的渐变、玻璃拟态、卡片堆叠、发光边框、默认配色、通用 HUD、伪装成精致的空洞装饰 |
| 文案 | 万能开场、空泛形容、机械排比、过度解释、假装幽默、重复情绪价值、没有具体信息的漂亮句子 |
| 交互 | 一切做成按钮/卡片/表单/面板；流程过度规整；缺少有意义的操作反馈与交互个性 |
| 内容 | 看似丰富却没有作用的物件/设定/剧情/数值/系统；堆积但无因果 |
| 设计 | 无取舍、无反常识的合理设计、无真实约束、无作者立场；习惯性选择最安全最易生成的方案 |
| 生产 | 反复生成相似候选、靠提示词换皮、把产量当质量、缺少真实筛选与整合 |

## 七条概念边界（去 AI 味 ≠ …）

不拒绝 AI ・ 不要求全部手工 ・ 不刻意做旧做粗糙做复古 ・ 不强推某种独立游戏风格 ・
不靠复杂化系统/堆世界观/堆细节 ・ 不把每款游戏改成同一种"高级审美" ・ 不消灭一切常见设计模式。

**有理由的设计留下；只为显得独特而奇怪的设计同样淘汰。** 反模板不是为了反模板。

## 机制的从属关系

| 机制 | 它应当解决的问题 |
| --- | --- |
| G1 视觉 Token 闭合文法 | 视觉语言失控、无意识套用默认风格 |
| G2 设计模糊测试 | 实际页面的结构性缺陷（溢出/截断/挤压） |
| G3 三件召回器 | 找出可能的重复与模板化痕迹 |
| G4 小批盲排序 | 检验设计判断是否可靠 |
| G5 否决语料库 | 不重复已证实的错误 |
| G6 印刷后处理链 | 为适用素材提供真实制作能力 |
| G7 判断校准 | 检验审美判断是否稳定 |
| 法庭 | 解决真正重要的争议与证据问题 |
| 三省六部 | 协调工作与执行责任 |

每个机制的六问体检（减少哪种 AI 味 / 证据 / 误判 / 成本 / 更简单替代 / 取消后是否变差）见
`MECHANISM_RESULTS.md`。**答不出六问的机制，不因"已投入很多"而保留。**

## 结果导向的评估原则

- 研究对象尽量是**真实页面、真实交互、可运行构建、真实资产**，不是只有文档与运行记录。
- 同一项目**修改前后对照**：截图、版本、实际页面、玩家反馈。
- 观察项：能不能感到独立身份 / 项目间是否同质 / 视觉是否与玩法世界观有真实联系 / 文案是否具体可信 / 交互是否有节奏性格 / 资产是否真的进了游戏并改善整体 / 去 AI 味有没有牺牲可读性易用性性能效率 / 改动能被真实游玩感知。
- **不把主观审美判断包装成客观科学结论，不用单一数字代替完整评价。**

## DE-AI 自身的约束（它也要接受去 AI 味审查）

不加层级/部门/角色/审批流程 ・ 不把普通设计问题变成制度议题 ・ 不用漂亮术语掩盖无效机制 ・
不重复开发已有工具 ・ 不把文档/规则/测试数量当成果 ・ 不把创作变成同一套提示词流水线 ・
不让人用 DE-AI 比自己干更麻烦 ・ 不为了维护既有方案而拒绝承认失败。

> 如果架构越来越复杂而游戏没有变好，那就是系统自身的失败。

## 研究优先级（自本协议起）

1. **真实去 AI 味效果**（作品层面可感知的改善）
2. **工具有效性**（能不能真的抓到问题、误判率）
3. **跨项目适用性**（两个以上项目复现才升级为通用）
4. **成本控制**（Token、人工、维护）

## 项目独立性

各项目视觉语言、文案风格、玩法结构、设计哲学都可以完全不同。DE-AI 帮它们各自摆脱模板化，
**不是让它们看起来像同一个团队做的**。单项目成功经验不自动成为别项目的强制标准。

## 架构冻结（2026-11-15）

当前架构冻结：不再新增机制、部门、角色、审批层级；不新增大规模文档。
后续工作只有两件事：维护现有能力、降低使用成本——以及等真实项目提要求时再动。

## 结果表述纪律

任何"某机制更好"的结论必须**分维**写（视觉一致性 / 入口可用性 / 综合作品质量 / 成本），
不得把"某一维更优"合并成"整体更好"；没有测到的维度必须写"未测"。

## 版本迭代的说明义务

以后每次改 DE-AI，必须能回答：**这次修改如何帮助解决"AI 味"这个原始问题？**
答不出来（或只让架构更好看）的修改，不做。
