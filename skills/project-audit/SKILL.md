# 现状审计（只读）

## 什么时候用

- 要重构或继续一个停了几周的项目。
- 别人（或上一个模型、上一份文档）说「已完成」。
- 文档目录与磁盘目录对不上；准备向用户报进度。

## 铁律

1. **0 行改动也算交付。** 审计只读，产出问题清单；先审后改，不许边审边改。
2. **文档会撒谎。** 三份文档写 `scenes/` 金乌案，磁盘上是 `game/` 码头失物案。以磁盘、`git log`、测试输出为准。
3. **全绿 ≠ 能玩。** 三代测试全绿，一次通关只触到 15% 的代码；测试覆盖不等于路径可达。
4. **不信自称完成。** 要有文件、有 commit、有真机操作；「已实现」必须指到文件与行号。

## 产出格式

| # | 问题 | 证据（文件:行 / 命令输出） | 与文档冲突？ | 处置 A/B/C/D |

A=接着做，B=降级为素材，C=归档，D=退役。每条给复现步骤，不写「建议优化」这类空话。

## 检查清单

- [ ] 目录树：文档提到的路径逐个 `Test-Path`，列出缺失项。
- [ ] git：最后 commit 时间、是否有未提交改动、本地是否落后远端。
- [ ] 入口：主场景 / 主文件能启动吗？（headless 跑一次，记报错原文）
- [ ] 测试：跑一遍，记通过数、失败项；标出「没有任何测试覆盖的入口」。
- [ ] 资产：引用的图片 / 模型 / 音频是否存在——缺文件比缺代码更常见。
- [ ] `TODO` / `FIXME` 计数 + 最老一条的日期。
- [ ] 把「已完成」的说法逐条对到文件证据，对不上的写进冲突表。

## 反例

- 直接接着写新功能，三天后发现底层是另一个案子的代码。
- 用「测试全绿」向用户报完成，用户一玩就撞到闪退。
- 日志每帧写盘冲掉现场（1065 行、742 条重复）→ 取证要在修复之前，独立 session、归档、不截断。
