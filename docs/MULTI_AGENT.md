# 多执行端并行：一个游戏工程，几个 AI 同时改

在一个人 + 几个编码 Agent 的配置下，最容易出的不是「AI 写错代码」，是**两个人同时改同一个场景文件，然后谁也说不清哪边是它想要的**。下面这套是我们实跑过一轮的做法，去掉具体模型名，可以直接抄。

## 结构：一个主控，多个执行端

| 角色 | 干什么 | 不该干什么 |
|---|---|---|
| **主控（Lead）** | 拆任务、派单、裁决冲突、跑测试总门禁、合入 | 不亲自写细分模块的实现 |
| **执行端 A** | 核心机制（玩家、相机、主要状态机） | 不碰 UI 样式与素材 |
| **执行端 B** | UI / 视听 / 素材管线 | 不碰核心机制脚本 |
| **执行端 C** | 测试、审计、独立 diff 审查 | 不写被审查的功能本身 |

关键不在分工的名字，在**每个执行端有一份写死的、独占写入的文件域**。写进派单表里，越界就是驳回，不讨论。

## 铁律一：不共享工作树

多个 Agent 在同一个工作目录并发改码，冲突不是「可能」，是「什么时候」。用独立的 Git worktree：

```bash
git worktree add ../wt-a -b agent-a/<topic>
git worktree add ../wt-b -b agent-b/<topic>
```

分支命名 `<端>-<主题>`，一个主题一个 worktree，合完就删。主控在集成主干上联调，不在执行端的 worktree 里改东西。

## 铁律二：冲突面先定契约

两个执行端必然要在某处交汇（场景里的信号、共享的数据结构、同一份配置）。**先定契约，再各自写**：

- 谁发信号、谁收信号，信号名与参数表写进派单；
- 数据结构（字段名、类型、默认值）写进派单；
- 谁负责把两边接起来 —— 通常是主控在集成树上做，不让 A 去改 B 的文件。

两个端同时要改同一个 `.tscn` / 核心脚本，是设计还没想清楚的信号，不是排期问题。

## 派单七要素

每张派单必须能独立作答，缺一项就别派：

1. **执行端与模型** —— 谁做，用什么
2. **任务目标** —— 一句话说清交付物，不是「优化一下」
3. **输入文件精确路径** —— 它能读到什么
4. **允许写入的输出白名单** —— 它能写什么（越界即驳回）
5. **前置依赖** —— 需要哪些东西已经就位
6. **客观验收标准** —— 第三方能照着执行判定的那种，不是「看起来更好」
7. **是否允许合入正式工程** —— 多数派单的答案是「不许，先出分支」

第 6 条最容易糊。反例：「UI 更舒适」；正例：「1440×900 与 390×844 两档截图，能看清三层信息，无溢出，无遮挡可交互元素」。

## 合并门禁四步（顺序不能换）

1. **越界检查**：`git diff --name-only` 与派单白名单比对；顺便查密钥、临时文件、调试开关残留。
2. **独立审查**：不写这段代码的人（或执行端 C）看 diff，出审查回执；审查只说「没问题」不算回执。
3. **全量测试**：主控在集成树上跑完整测试集，断言数不低于基线；UI 改动必须过实机截图视觉审查（能看到图的审查，不是读代码想象）。
4. **合入**：前三步都过才合；合完删 worktree 与分支。

任何一步不过，退回去重做，不「先合了再补」。

## 失败与重试

- API 超时 / 5xx：保留 worktree 落盘进度，最多自动重试 2 次。
- 通道持续不可用：切备用模型并在日志里写明换了谁、为什么，**不允许伪造并行回执**（「三个 Agent 都跑完了」这种话，要么有回执，要么不说）。
- 执行端报「完成了」但证据不足：按 `task verify` 的清单逐项核，缺项打回。

## 反例（都是真踩过的）

- 两个执行端同时改同一个主场景 → 合并时丢掉一方的全部改动，且没有报错。
- 执行端自己起了开发服务器 / 占了固定端口 → 主控的验证脚本连到旧进程，测的是上一版。
- 派单里写「参照 `docs/DESIGN.md`」但没有该文件，执行端自己编了一套 → 白做一轮。
- 主控一边派单一变得顺手自己也去写实现 → 没人再做总门禁，测试从 27 条掉到 24 条没人发现。

## 什么时候别并行

一个人能串行做完的量（≤ 半天），并行的协调成本比省下的时间大。并行只在两个条件同时成立时值得：**任务能被切成互不写同一批文件**，且**有一个人专门做门禁**。
