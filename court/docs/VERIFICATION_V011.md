# 独立验收升级报告（V0.1.1 P0-4）

## 问题（C-001 暴露的）

C-001 的 T03（独立核验）虽然抓到了执行者在归一化统计里的重复相加错误（26 条 `clamp()` 在 FONT 与 FONT-RESPONSIVE 两类里被加了两次，70/22.3% 应为 44/14.0%），但它当时**靠的是核验人认真**，程序上没有任何东西强制它「打开原始材料、核对版本、复算内容」。换句话说：C-001 的验收是可敬的个人行为，不是可复制的过程。

## V0.1.1 的做法

`verifyTask` 现在要求三个必填项，缺一项就 `VERIFY_CHECKLIST_INCOMPLETE`：

| 字段 | 含义 | 为什么是它 |
|---|---|---|
| `artifactsOpened` | 是否直接打开原始材料（不是只看报告） | 报告里写的百分比与材料是两回事；C-001 的错误正好藏在「报告 §7」而不是材料里 |
| `versionChecked` | 是否核对了版本/commit/文件 sha | 同一份报告可能对应旧材料；没有版本锚，复算无法定位 |
| `contentRechecked` | 是否独立复算了内容（不是转述执行者的话） | 「转述」是验收最常见的退化方式 |
| `recomputed` / `doubleCountChecked` / `omissionChecked`（至少一项为真） | 三类针对性检查 | 分别对应 C-001 的三种错法：算错、重复计数、选择性遗漏 |
| `artifacts[]` | 原始材料路径，必须存在 | 引擎把每个路径的 sha256 写进案卷，第三方事后可复算 |

另外：`note ≥20 字`；验收人 = 执行人 → `SELF_VERIFICATION`；材料在验收后被删 → 审计 `TASK_EVIDENCE_GONE`。

## 对 C-001 的追溯处理

**不回填。** C-001 的 T03 已按 V0.1 记录入档（`stage=closed`），V0.1.1 不重判、不补写 checklist。原因：改写历史会让「当时到底查了什么」永久不可知，而这份不可知本身就是教训。作为替代，C-001 的 T03 报告留档，并在 `CASE_REPORT.md` 里注明「该次验收未走 checklist，属 V0.1 口径」。

## C-002 的验证（本轮实跑）

C-002 的执行任务采用同一套 checklist（见 `cases/C-002/case.json` 的 `tasks[]`）。若验收人是 lead 本人（提案作者），引擎会直接拒——所以 C-002 的验收必须另派独立 subagent，或由用户本人做。本轮采用独立 subagent（`c002-verifier`）。

## 残余问题

1. `artifacts[]` 只存 sha，不存内容快照；若原文件被覆盖，sha 会失配但也无法复原（`TASK_EVIDENCE_GONE` 只能报警）。
2. checklist 三项是「勾选式」的，仍可能被勾选而没有真做——这一点无法用程序解决，只能靠「独立的人 + 事后审计 + 少量抽查」。
3. 未覆盖：验收人**资质**（谁有资格验收）没有规则；本轮默认「不是执行人、不是提案作者」。
