# 提案：在 bistro-rush 试点闭合文法（G1）

## 问题

`bistro-rush` 的视觉值没有上游声明：颜色、圆角、字号、间距、阴影全部直接写在 ~7600 行 `src/ui/styles.css` 以及组件内联样式里。后果不是"不好看"，而是三件事都做不到：

1. 无法回答"这个值从哪来"（溯源）；
2. 无法在新屏里拒绝一个新的魔法数字（闭合）；
3. 每次改版都可能引入第 31 种字号，而没有任何地方会报错。

## 提案（最小版）

新增一个**只读编译层**，不碰现有 UI：

1. 从现有 CSS 里抽一份 `style.json`（≤80 行）：`premise`（这款游戏为什么长这样，1–2 句）、`roles`（角色表：文字/底色/纸/强调/危险…，每个角色 1 个值 + 允许的派生规则）、`bans`（≤7 条，例如"不加模糊阴影"）、`constitution`（1 条绝不允许的事）、`forced-tension`（1 条强制不规则，例如"每屏至少一个非 4 倍数间距"）。
2. `build-check.mjs`：扫描 `src/**/*.css` 与 `*.tsx` 的样式字面量；**任何未在 `style.json` 声明、且不匹配派生规则的值，输出 `文件:行` 并以非 0 退出**。
3. 只在实验目录跑（`_research/court_case_c001/pilot/`），先把现有代码的违规列成清单，不修改 `bistro-rush` 一个字节。

## 判定成功/失败（试点前写死）

- **成功**：能在一屏新界面上，只用 `style.json` 里声明的值完成实现，且 `build-check` 0 新增违规；人工时间 ≤2 小时。
- **失败（任一）**：①`style.json` 无法在不失真表达现有设计的前提下压到 80 行；②`build-check` 对现有代码报出 >300 条违规，说明闭合门槛与现实差距过大；③试点后再写新屏仍需要 3 个以上新魔法数字；④总人工 >4 小时。

## 不做

- 不改 `bistro-rush` 源码；
- 不引入依赖、不新增服务；
- 不把《小泽模拟器》的规则搬过来当通用法律。
