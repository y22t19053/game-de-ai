## 三、五问回答

**Q1 V0.2.0 是否完成？**
基本完成，但有一处不能算完：**C-003 的 pilot 未执行**（T01 六张双档实拍没做、T02 需用户裁决）。其余项目全绿。所以准确说法是「程序与实测已交付，C-003 执行未开、未结案」。

**Q2 普通创作能否不经法庭？**
能。实测 3 件普通任务全部走「提案 → 门下省日常审核 → 退回/升级」，**0 件开庭**，人工步骤各 1–3 步。其中 1 件（圆角归一）因命中「实质分歧」被升级并入 C-003——这不是误分流，是判据按设计工作。

**Q3 法庭是否处理过有价值争议？**
是，且抓到的是**人凭记忆会错、读源码才知道**的那类问题：
- C-004：提案的 B 清单前提（成品有一枚"已阅"章）在成品里**不存在**（`stamp`/`已阅` 零命中）；ΔL 2.1 是假数字（实测 7.19 / 5.99）；页脚"8px 两段"是从原型误引（实为三段、`gap:6px 18px`）。
- C-003：25% 判据**在改造前就已通过**，不具证伪力；47 圆角里 66 次是语义值。
这两案的价值不在"投票结果"，而在**质询阶段双方靠证据互相削弱了自己的初始主张**。

**Q4 实际增加多少成本？**
能真报的：C-001 开庭→裁决 **82 calls / in 93,431 / out 72,165**；C-002 开庭 80 calls（87,071 / 39,341）；C-002 陪审→裁决→结案 101 calls（84,421 / 54,271）。**C-003/C-004 未插桩 → `unavailable`**，不写 0、不反推。模型名与 API 单价不在会话日志里 → `apiCostCNY` 恒 `unavailable`。定性结论：**法庭的单案人工成本明显高于"顺口讨论"**（C-004 约 20 个人工步骤、95 分钟），它的价值只在"这个决定值得付这个价"时才成立。

**Q5 是否具备开始改进两个游戏的条件？**
具备，但**顺序建议**：先做两款计划里各自的硬伤（bistro：晚上星数算法错误 + 五屏 header 重复；小泽：ops 面板被 32 张预设卡撑到 2903px），这两项**不需要开庭**（普通路径即可）；C-003 的 B 方向要先等你对 A/B 的一句书面裁决，再考虑是否值得开 pilot。前提是：**不改正式版、先出副本/截图，改动逐条挂文件:行**。

## 四、成本缺失说明（必须读）

- 会话日志可解出 `usage.inputTokens/outputTokens/cacheReadTokens`，**这是唯一的真数字来源**；`cacheRead` 数量级远大于 input/output，容易被误当成本主体。
- 逐案耗时只能按**时间窗**切（本案按 `time` 字段切出 C-001/C-002 窗口），C-003/C-004 没有单独切 → 记 `unavailable`。
- 人工步骤/分钟是**我自己记的**，不是机器测的，属"自报口径"，已在 `COST_V020.md` 标注。

## 五、停止条件（按用户要求写死）

V0.2.0 之后**停止法庭集中开发**：不新增角色、不新增程序、不做与创作无关的制度研究；只修真实使用中的重大问题（如 I-25 这类"裁决形态与缺陷不符"的）。下一步转入两款游戏的实际改进，交付形态是**截图与 diff**，不是制度文档。
