# 制度治理架构 V0.1

> 对象只有 GAME DE-AI 本身。法庭不是第四省、不是第七部，而是**横向独立审查层**：日常由三省六部走，争议才进法庭。

## 1. 为什么需要它（继承 V0.3，不复述研究报告）

V0.3 七轮否定留下的三条硬证据：

1. **人工评审会漏**：`bistro-rush` 两轮人工评审都没发现 74 组跨文件重复句式，一只 100 行的脚本 3 秒就列出来了——但脚本的口径本身也被 R1/R2 推翻（"74"是旋钮，4-gram 分辨率地板）。所以：**仪器给候选，裁决要人（或制度）。**
2. **提示性的"再加一道审查"会退化成补论证**：同一上下文下的第二遍审阅，倾向给第一遍找理由（门下省两轮抓到的 13 处硬伤，全部来自**独立上下文**的 subagent，而不是我自己的复读）。
3. **书面结论会漂移**：我自己在报告里连续三次把回执算不平、把 14 字写成 17 字。凡是没有被**独立验收**的"完成"，都会变成新的事实。

所以制度的三个基本零件不是角色名，而是：**独立上下文、可核验的证据、不能自证的验收**。

## 2. 四层结构

| 层 | 管什么 | 不管什么 | 产物 |
|---|---|---|---|
| 文法层（闭合 Grammar） | 每款游戏一套声明式的视觉/语言词汇：未声明的值不得出现 | 不判好坏 | `style.json` → 编译出 CSS 变量 / Godot theme |
| 仪器层（Instruments） | 只读扫描：重复句式、token 漂移、字号/圆角分布、文案清单、引用图 | 不裁决、不进验收 | 候选清单（每次 ≤5 条，附 `文件:行`） |
| 议事层（三省六部） | 日常提案—封驳—执行 | 不审自身重大争议 | 票拟、封驳单、执行记录 |
| 法庭层（Court） | 重大争议、关键决策、权限越界、利益冲突、证据争议、严重程序违规、重大失败责任、推翻先例的申请 | 不接管日常、不重复门下省普通审核 | 案件档案、裁决、执行任务、先例 |

**门下省 vs 法官**：门下省是**日常封驳**（三案阶段就介入，判"是否模板化/是否伪差异"）；法官是**争议裁决**（只处理已经上升到案件的分歧，管程序与证据资格，不替任一方补论据）。两者都不许是本案方案作者。

## 3. 角色与权责

| 角色 | 回答什么问题 | 权力 | 禁止 |
|---|---|---|---|
| 皇帝（用户） | 我要什么、我接受什么代价 | 终裁、改判、要求重审、指定试点 | —— |
| 内廷承旨（主 Skill） | 这是讨论、探索、案件还是执行 | 分流、登记案件、派单 | 不得替皇帝决定方向，不得自任法官 |
| 检察方 | 这个方案哪里会失败、哪里在夸大 | 指控、要求补证、质询 | 不得只堆挑刺数量；每条指控须挂证据编号 |
| 辩护方 | 这个方案凭什么成立 | 反驳、补证、质疑证据资格 | 不得隐瞒重大风险换取批准 |
| 法官 | 争议焦点是什么、证据算不算数 | 定焦点、裁证据资格、写裁决、派执行任务 | 不得兼任方案作者/控辩任一方；不得替控辩补论据 |
| 陪审团（≥3，major≥5，high≥5） | 读完意见前我自己的判断是什么 | 独立投票、保留少数意见 | 不得同一上下文复制多个投票窗口；不得只投票不写理由 |
| 书记员（= 程序本身） | 这件事可追溯吗 | 追加式哈希链日志、档案、先例索引 | 无改判权；不得改写历史条目 |
| 制度攻击方 | 制度自己能被怎么击穿 | 在隔离环境发起攻击 | 不得篡改正式档案、删证据、对外欺骗 |

## 4. 分流规则（承旨三问）

1. 这是**讨论/检索**吗 → 直接答，不立案。
2. 这会改变**已确认的视觉方向、设计规则、资源投入、对外发布**吗 → 立案。
3. 争议双方的**主张是否有证据支撑冲突** → 有则进法庭；没有则先补证（`stay`）。

案件类型与门槛（写死在 `src/court.mjs` 的 `CASE_TYPES`）：

| 类型 | 典型触发 | 陪审 | 交叉询问 | 附加 |
|---|---|---|---|---|
| ordinary | 单个界面/单条文案/单个素材的改或不改 | ≥3 | ≥1 | —— |
| major | 核心架构、技术路线、设计规则、重要资源 | ≥5 | ≥2 | 需成本收益与反事实 |
| high | 不可逆、核心制度变更、重大失败追责、严重利益冲突 | ≥5 | ≥3 | 需制度攻击记录 + 七轮说明 |

## 5. 七轮的位置（不是默认流程）

七轮否定降级为**高风险案件的取证工具**，不再每次创作都跑：

- 只有 high 案、或 major 案中控辩对"失败路径"存在实质分歧时才调用；
- 每一轮必须在案卷里写清：攻击目标、预期证据、停止条件；
- 无新证据时必须写"本轮无新增"，不许凑轮数；
- 调用几轮由法官在裁决里写明理由（`roundsChosen` + `roundsWhy`），审计会查。

## 6. 与三省六部的接口

```
皇帝 → 承旨分流 ─┬─ 日常：中书三案 → 门下封驳 → 尚书调度 → 六部/工部执行 → 御前预览
                └─ 争议：登记案件 → 控辩 → 交叉询问 → 陪审 → 法官裁决 → 执行任务 → 独立验收 → 先例
```

- 法庭**不产出设计**，只产出裁决与执行条件；
- 裁决落地仍走尚书省派单、工部实施；
- 门下省封驳单可作为案件证据（类型 `expert`），但不能代替陪审；
- 先例只向法庭与门下省开放引用，六部不得自行"依法"套用别的项目规则。

## 7. 未解决问题（不填默认值）

1. **独立性的真实程度**：不同 subagent 仍是同一底模。目前只有"独立上下文 + 不同输入包"这一层隔离；模型层的独立性未验证。
2. **陪审的统计意义**：n=3 只能防"一人说了算"，不能防"系统性同偏"。
3. **Token 与人工时间的真实成本**：本原型记录 agent 数与墙钟，未插桩 token；A/B 对照的 token 列只能给估算区间并标注。
4. **法官的中立性**：法官也是模型，可能被"看起来更完整的书状"带走（verbosity bias）；需要未来的位置随机化实验。
